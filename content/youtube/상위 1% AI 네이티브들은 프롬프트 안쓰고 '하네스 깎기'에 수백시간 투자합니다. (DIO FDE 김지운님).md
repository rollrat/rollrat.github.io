## 상위 1% AI 네이티브들은 프롬프트 안쓰고 '하네스 깎기'에 수백시간 투자합니다. (DIO FDE 김지운님)
> 📅 2026-03-24 | ⏱️ 43.5분 | [영상 링크](https://www.youtube.com/watch?v=A8PMyC7W_vg)

### 핵심 요약
- **하네스 엔지니어링**이란 프롬프트가 아닌 구조·규칙·린터를 통해 어떤 AI 모델(Claude, Codex, Gemini)을 써도 동일한(멱등한) 결과물을 강제하는 기법이다.
- 엔터프라이즈 AX(AI Transformation) 현장에서는 바이브코딩이 아닌 **6단계 워크플로우**(요구사항 → 플랜 → CPS → PRD/설계 → 코드+린터 → 평가)로 강건한 소프트웨어를 빌딩한다.
- 코드 레벨에서 파일명·임포트 순서·익스포트 규칙 등을 **린터로 강제**하면 AI가 생성하는 코드도 일관성을 갖게 되어, 유지보수 인수인계 시 휴먼 리더블한 산출물을 보장할 수 있다.
- 조직별 맞춤 **이밸류에이션(평가) 프레임워크**를 구축해 AI 에이전트의 답변 품질을 지속적으로 모니터링하는 것이 엔터프라이즈 AI의 핵심이다.
- FDE(Forward Deployed Engineer)는 고객사에 파견되어 요구사항을 MECE하게 분석하고, 제로투원을 함께 구현한 뒤 내부 인원이 자립할 수 있도록 무기(문서·린터·평가체계)를 세팅해주는 역할이다.

### 주요 내용

#### 엔터프라이즈 AX와 FDE의 역할 (0:27~5:20)
- 스페이스와이(SpaceY) 황현태 대표와 김지운 FDE가 출연. 엔터프라이즈 AX 경험을 공유하는 유튜브 '까칠한 AI'도 운영 중.
- FDE(Forward Deployed Engineer)는 고객사에 직접 파견되어 주 2~3회 미팅하며 요구사항을 정의하고 제로투원을 함께 구축하는 역할.

#### 하네스 엔지니어링과 멱등성 개념 (5:21~6:40)
- **멱등성(Idempotency)**: 같은 입력을 넣으면 항상 같은 출력이 나오는 성질. AI 모델이 바뀌어도 동일한 결과물을 보장하는 것이 목표.
- 하네스 엔지니어링 = 프롬프트 엔지니어링을 넘어, 구조·규칙·검증 체계를 통해 결과물의 방향을 강제하는 기법.

#### 6단계 플로우 (6:41~12:52)
1. **요구사항 수집**: 고객의 비정형 요구를 자유롭게 받음. "제한하지 않는다"가 미팅 원칙.
2. **플랜**: 미팅 로그를 구조적으로 정리. 매 미팅마다 직전 완성물 + 오늘 할 일 리뷰.
3. **CPS(Context-Problem-Solution)**: 맥락·문제·솔루션 프레임워크로 사고 정리. 팔란티어의 머드 세션에서 영감.
4. **PRD/설계**: 원칙 수립 → 개념 정의 → 구조 설계 → 데이터 흐름 설계. 도메인 드리븐 디자인 채택.
5. **코드 + 린터**: 린터로 파일명·임포트·익스포트 규칙 강제.
6. **이밸류에이션**: 조직 맞춤 평가 지표로 품질 지속 모니터링.

#### 문서 산출물의 전략적 활용 (12:53~17:51)
- 문서는 POC 기간 중 2번 공유: 1차 스펙 확정 시 + 프로젝트 완료 시(역기획).
- 고객사가 구현 세계관을 이해해야 더 좋은 아이디어를 낼 수 있어 PDF 문서를 적극 공유.
- 마크다운 → LaTeX 템플릿 → PDF 빌드 파이프라인 활용.

#### 설계 문서의 핵심과 원칙 세우기 (17:52~21:49)
- 프로젝트마다 대전제 원칙 수립 (예: 휴먼인더루프, 할루시네이션 제거, 로그 관리).
- 개념 정의 → 하이어라키 설정 → 구조 설계 → 기술적 데이터 흐름 설계 순서.
- 유저 멘탈 모델까지 설계 문서에 포함.

#### 팀 내 멘탈 모델 공유와 협업 (21:50~27:05)
- 코딩 컨벤션이 아닌 **멘탈 모델 일치**에 집중. 프로젝트마다 KPI와 제1원칙이 다르기 때문.
- 모든 산출물은 GitHub 팀 레포에 오픈, 로그는 노션, 커뮤니케이션은 슬랙.
- 주간 고정 요일에 모여 설계 리뷰 → 집단지성 형성.

#### 린터를 활용한 코드 강제화 (27:06~31:09)
- 도메인 관점에서 파일명 강제 (예: `restaurants` 복수형, `detail`/`list` 금지).
- 임포트 알파벳 순서, 임포트 가능/불가 파일, 배럴 파일 규칙 등 린터로 통제.
- 커밋 시 자동 린터 실행 → AI가 규칙 위반을 스스로 감지하고 수정.
- 3개 모델(Claude, Codex, Gemini) x 4개 소프트웨어 = 12개 결과물이 동일한 아웃풋.

#### 유지보수와 휴먼 리더블 코드의 가치 (31:10~36:19)
- 바이브코딩으로 엔터프라이즈 구축 후 유지보수까지 넘어간 사례는 아직 없음 (시기적으로 6개월 미만).
- 유지보수를 SI 팀이 받을 수 있도록 휴먼 리더블한 코드와 가이드라인이 필수.
- AI가 읽기 편한 스타일과 인간이 읽기 편한 스타일 사이의 트레이드오프 존재 → 인간 협업 우선.

#### 조직 맞춤 AI 평가(Evaluation) 체계 (36:20~41:04)
- 기본 4가지 지표: 문맥 적합성, 정확성, 소스 데이터 적절성, 누락 여부.
- 조직마다 허용 오차가 다름 (100번 중 1번 틀려도 OK vs 20번 틀려도 답변은 해야 함).
- "에이전트 도그(Agent Dog)" 개념: DataDog처럼 AI 에이전트 품질을 매일 모니터링.
- 고객사별 맞춤 이밸류에이션 메소돌로지 설계 후 납품.

#### 김지운 FDE의 하드웨어 경험과 멱등성의 기원 (41:05~43:00)
- 과거 하드웨어(PCB+펌웨어) 프로젝트 실패 경험: 문제 발생 시 "포맷해라"라는 답변을 반복적으로 들음.
- 제로부터 다시 쌓아야 하는 고통에서 "필연적인 결과로 가는 단계가 멱등해야 한다"는 철학이 형성.

### Q&A

**Q1. 하네스 엔지니어링과 프롬프트 엔지니어링의 차이는 무엇인가?**
프롬프트 엔지니어링은 AI에게 좋은 질문을 던지는 데 집중하지만, 하네스 엔지니어링은 프롬프트 외에 린터·설계 문서·디자인 시스템·평가 체계 등 구조적 장치를 통해 어떤 AI 모델을 사용하든 동일한 결과물이 나오도록 강제하는 상위 개념이다. 프롬프트만으로는 100% 일관성을 보장할 수 없기에, 코드 커밋 시 자동으로 실행되는 린터나 원칙 문서가 보완 역할을 한다.

**Q2. 소규모 팀이나 개인 개발자도 하네스 엔지니어링을 적용할 수 있는가?**
핵심은 규모가 아니라 "원칙을 세우고 자동으로 검증하는 체계"를 만드는 것이다. 개인 개발자라도 ESLint 커스텀 룰, 파일명 컨벤션, 커밋 훅 등을 설정하면 AI가 생성하는 코드의 일관성을 크게 높일 수 있다. CPS(Context-Problem-Solution) 프레임워크 역시 혼자서도 사고를 정리하는 데 유용하다.

**Q3. 엔터프라이즈 AX 프로젝트에서 가장 흔한 실패 원인은 무엇인가?**
영상에서 언급된 핵심 실패 요인은 "유지보수 고려 없는 구축"이다. 바이브코딩으로 빠르게 만들더라도, 내부 인원이 이어받을 수 있는 문서·린터·평가체계가 없으면 6개월 후 유지보수가 불가능해진다. 또한 조직별 맞춤 평가 지표 없이 범용적인 AI 평가만 적용하면 실제 비즈니스 요구와 괴리가 생긴다.
