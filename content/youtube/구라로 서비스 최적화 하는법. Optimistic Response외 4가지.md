## 구라로 서비스 최적화 하는법. Optimistic Response외 4가지
> 📅 2026-02-16 | ⏱️ 18.3분 | [영상 링크](https://www.youtube.com/watch?v=-ClyAqH4yGo)

### 핵심 요약
- **낙관적 응답(Optimistic Response)**: 서버 응답을 기다리지 않고 성공을 가정해 UI를 즉시 업데이트하고, 실패 시에만 롤백하는 패턴
- **업로드 퍼스트 패턴(Upload First Pattern)**: 사용자가 파일을 선택하는 순간 즉시 임시 버킷에 업로드해두고, 폼 제출 시에는 텍스트 데이터만 전송해 체감 속도를 높이는 패턴
- **백그라운드 서브미션(Background Submission)**: 업로드 시 로딩 블로킹 없이 바로 결과 페이지로 이동시키고 상단에 진행 상황만 표시해 사용자가 동시에 다른 작업을 할 수 있도록 하는 패턴
- **프리사인드 URL(Presigned URL)**: 서버를 거치지 않고 클라이언트가 클라우드 객체 스토리지에 직접 업로드할 수 있도록 서버가 서명된 임시 URL을 발급해주는 방식
- **클라이언트 사이드 압축**: 업로드 전 WebP/AVIF 등으로 이미지를 브라우저에서 직접 압축해 파일 크기를 줄이고 업로드 속도를 향상시키는 방법

### 주요 내용

#### 00:00 - 02:02 | 해결하려는 문제
서버 최적화의 핵심 문제는 네트워크 레이턴시다. 클라이언트↔서버, 서버↔DB 사이에는 물리적으로 피할 수 없는 지연이 존재한다. 이미지·동영상 등 대용량 파일을 포함하면 지연은 더욱 커진다. 고사양 서버나 CDN을 쓰면 빨라지지만 비용이 따른다. 이에 **알고리즘 최적화가 아닌 비즈니스 관점의 착시 전략**으로 사용자 체감 속도를 높이는 5가지 테크닉을 소개한다.

#### 02:03 - 06:22 | Optimistic Response (낙관적 응답)
프론트엔드에서 유효성 검증을 충분히 했다면, 백엔드 요청도 어차피 성공할 것이라고 가정한다.

1. 폼 제출과 동시에 **로컬 캐시를 즉시 업데이트** (성공한 것처럼 UI 반영)
2. 이전 상태를 임시 저장해 **롤백 대비**
3. 서버로 실제 API 요청 전송
4. 성공 시 → 서버 반환값(ID, URL 등)으로 백그라운드 동기화
5. 실패 시 → 임시 저장한 이전 상태로 롤백 + 에러 메시지 표시

좋아요 버튼처럼 단순한 CUD 작업에 특히 효과적이다. 캐시 싱크가 복잡한 작업에는 무리해서 적용하지 않는 것이 좋다.

#### 06:23 - 10:29 | Upload First Pattern
이미지·동영상을 포함하는 폼에서 체감 업로드 속도를 획기적으로 줄이는 패턴.

1. 사용자가 파일을 **선택하는 순간** 임시(temp) 버킷에 즉시 업로드 시작
2. 클라이언트는 업로드된 파일의 경로/ID만 저장
3. 사용자가 제목·내용 등 나머지 텍스트를 입력하는 동안 **백그라운드에서 업로드 완료**
4. 제출 버튼 클릭 시 텍스트 데이터 + 파일 경로만 전송 → 거의 즉시 완료

> ⚠️ **주의**: 임시 폴더 파일은 주기적으로 삭제해야 불필요한 스토리지 비용 방지. 같은 버킷 내 `temp/` → `permanent/` 폴더 이동이 다른 버킷 간 복사보다 훨씬 빠르다.

#### 10:30 - 13:41 | Background Submission (비동기 제출)
업로드 버튼을 눌렀을 때 로딩 스피너로 화면을 막지 않고, **즉시 결과 페이지(목록 등)로 이동**시킨다.

- 상단에 소형 업로드 진행 컴포넌트만 표시 (인스타그램 방식)
- 사용자는 업로드가 진행되는 동안 다른 콘텐츠를 자유롭게 탐색 가능
- 대규모 서비스에서는 Redis/SQS/RabbitMQ 같은 **메시지 큐** + **백그라운드 워커(Lambda 등)** 를 결합해 CPU 집약적 작업(영상 인코딩, 대량 메일, PDF 생성)을 처리
- 완료 후 WebSocket 또는 폴링으로 사용자에게 알림

#### 13:42 - 16:12 | Presigned URL
클라이언트가 서버를 경유하지 않고 **클라우드 객체 스토리지에 직접 업로드**하는 방식.

기존 방식: `클라이언트 → 서버 → S3` (2번 전송, 느림)  
프리사인드 URL: `클라이언트 → (서버에서 URL 발급) → S3 직접 업로드` (1번 전송, 빠름)

- 서버는 5~10분 유효한 서명된 임시 URL만 발급
- 클라이언트는 해당 URL로 S3에 직접 PUT
- 보안 키/시크릿 노출 없이 제한된 업로드 권한 부여
- 클라우드 엣지 네트워크 덕분에 어느 방식보다 빠름

#### 16:13 - 18:18 | Client-side Compression (클라이언트 사이드 압축)
파일을 업로드하기 전, **브라우저에서 직접 이미지를 압축**해 파일 크기를 줄인다.

- **WebP**: 대부분의 브라우저 지원, 범용적
- **AVIF**: 압축률 더 좋음 (동일 화질에 약 30% 더 작음), 일부 구형 브라우저 미지원
- 직접 구현 없이 JavaScript 라이브러리 활용 가능
- 데이터 비용 절감 + 업로드 속도 향상에 동시 기여

### Q&A

**Q1. Optimistic Response에서 롤백이 필요한 상황은 언제이며, 어떻게 처리하나요?**
서버 요청이 실패했을 때 롤백이 필요합니다. 구현 방법은 폼 제출 시 이전 상태(예: 좋아요 수)를 임시 변수에 저장해두고, API 요청 실패 응답을 받으면 해당 저장된 값으로 UI를 되돌립니다. 동시에 에러 메시지나 토스트 알림으로 사용자에게 실패를 알립니다. React Query나 TanStack Query 같은 라이브러리는 `onMutate`, `onError` 콜백으로 이 패턴을 기본 지원합니다.

**Q2. Upload First Pattern에서 사용자가 파일 선택 후 폼을 취소하면 임시 파일은 어떻게 관리하나요?**
임시 버킷의 `temp/` 폴더에 저장된 파일은 일정 시간(예: 3일) 후 자동 삭제되도록 S3 라이프사이클 정책을 설정하는 것이 표준 방법입니다. 폼 취소 이벤트를 감지해 즉시 삭제 API를 호출하는 방법도 있지만, 라이프사이클 정책만으로도 충분히 관리됩니다. 같은 버킷 내 폴더 이동(rename)이 버킷 간 복사보다 빠르므로, 반드시 **같은 버킷 내에서 temp/와 permanent/ 폴더를 분리**하는 구조를 권장합니다.

**Q3. 소규모 서비스에서 Background Submission에 메시지 큐(SQS 등)를 꼭 도입해야 하나요?**
소규모 서비스라면 굳이 메시지 큐를 도입할 필요는 없습니다. 단순히 서버에서 비동기 작업(async/await 없이 백그라운드 태스크로 분리)을 처리하고, 클라이언트에서 짧은 간격으로 폴링하는 방식도 충분히 효과적입니다. 영상 인코딩이나 대량 메일 발송처럼 처리 시간이 수십 초 이상인 작업이 빈번해질 때 Lambda + SQS 같은 구조를 고려하면 됩니다.
